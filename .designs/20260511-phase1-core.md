# tomori Phase 1 (Web 完結 MVP) Core Design

> 作成日: 2026-05-11
> 対象: Phase 1 のみ。Phase 1.5 (iOS ラップ) / Phase 2 (Calendar/Gmail) は本書末尾 §15 で骨格のみ言及し、本実装は別設計 doc に委ねる。
> 出力責務: Developer (Codex) がこの doc だけで実装でき、Reviewer (Codex) がこの doc だけからテストを生成できる粒度。

---

## 1. 目的

Touri Aida 個人の生活リズム改善を支援する AI 秘書「tomori」の **最小実用版を Web で完結** させる。朝/夜の AI 対話・任意 AI 相談・気分ログ・睡眠報告・階層型メモリで「効くか」を 2–3 週間で自分検証する。Push なし、能動起動。Phase 1.5 で Capacitor ラップしても破綻しない形 (Next.js `output: 'export'` 制約) で書く。

---

## 4. UI/UX (Phase 1)

### 4.1 デザイントーン

| 項目 | 値 |
|---|---|
| 基調 | **ライト** (明るめ、暖色ベース)。dark mode 切替対応 |
| 参照 | Day One / Stoic / Reflectly のジャーナル系トーン |
| aisaba 系との差別化 | aisaba 系はダーク・装飾排除・「::」付き見出し。tomori は柔らかいライト基調。**aisaba design language は適用しない** (knowledge/pattern/aisaba-design-language.md は参照しない方針を本書で明文化) |
| UI ライブラリ | **Tailwind + Konsta UI** (Konsta `theme="ios"` 固定。Phase 1.5 で iOS Liquid Glass に乗せる前提) |
| 角丸 | 16px (`rounded-2xl`) 大きめ |
| グラデ・blur | 控えめ。キャラ周辺と FAB 周辺のみ |
| マイクロアニメ | キャラ呼吸 (4s 周期 scale 1.00 ⇄ 1.04) / 対話パルス (返答中、scale + opacity oscillate) |
| マーケ語 | 禁止 (「画期的」「シームレス」等)。自虐 OK |
| 絵文字 | 出力テキストでは AI も含め控えめ。アプリ内ラベルでは使わない |

### 4.6 キャラ「光点 (orb)」の状態仕様

| state | 配色 | 動き | 起動条件 |
|---|---|---|---|
| `idle` | accent.300 → accent.100 へ放射 (柔らかい) | 4s 周期 scale 1.00 ⇄ 1.04 (breathing) | home 表示・対話以外 |
| `morning` | accent.500 → accent.50 (やや強め、暖色寄り) | 6s 周期 slow pulse + 上方向に微浮上 (translateY -2px) | `/morning` 表示中 |
| `evening` | accent.700 → accent.300 (落ち着き、深い琥珀) | 8s 周期 super-slow pulse | `/evening` 表示中 |
| `talking` | 現 state のまま + 1.5s パルス重畳 | LLM レスポンス受信中のみ | `streamingActive === true` |
| `crisis` | danger.500 を弱めにフラッシュ → idle に戻る | 1 回のみ 0.3s pulse | crisis card 表示瞬間のみ |

実装は CSS `@keyframes` で完結。Lottie / Rive は使わない (バンドルサイズ + Phase 1.5 WebView 安定性のため)。

### 4.8 状態管理

- **クライアント側**: Zustand store 1 つ (`apps/web/src/store/app.ts`)
  - `sessionUser: { id: string } | null`
  - `dialogSession: { id: string; mode: 'morning'|'evening'|'talk'; turns: TurnView[]; status: 'idle'|'streaming'|'closing'|'closed' } | null`
  - `crisis: { open: boolean }`
  - `theme: 'light'|'dark'|'system'`
- **サーバ側**: Postgres (`sessions`, `dialog_sessions`, `dialog_turns`, `mood_logs`, `sleep_logs`, `users`, `user_keys`, `dialog_summaries`)
- **localStorage 使用**: `theme` のみ。会話履歴やトークンは保存しない (XSS リスク回避)。
- **認証**: cookie ベース session (`Set-Cookie: tomori_sid=...; HttpOnly; Secure; SameSite=Lax; Max-Age=2592000`)
- **CSRF**: 同一オリジン (Nginx 経由で同 origin から `/api/*` を呼ぶ) + state-changing 動詞では `X-Tomori-Csrf` カスタムヘッダ必須 (cookie + custom header の double-submit)

## 5. データモデル

### 5.1 Postgres スキーマ (全テーブル)

エンコーディング: UTF-8。timezone: timestamps は **timestamptz** で UTC 保存、表示時に Asia/Tokyo へ変換。

```sql
-- users: Phase 1 は Touri 1 人だが、構造はマルチユーザー対応
CREATE TABLE users (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email        text NOT NULL UNIQUE,
  created_at   timestamptz NOT NULL DEFAULT now(),
  deleted_at   timestamptz                       -- 論理削除
);

-- user_keys: per-user DEK (KEK で暗号化済)
CREATE TABLE user_keys (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id        uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  dek_ciphertext bytea NOT NULL,                 -- DEK を KEK で AES-256-GCM 暗号化
  dek_nonce      bytea NOT NULL,                 -- 12 bytes
  kek_id         text NOT NULL,                  -- 'env:v1' / 'kms:arn:...'
  alg_version    smallint NOT NULL DEFAULT 1,
  created_at     timestamptz NOT NULL DEFAULT now(),
  retired_at     timestamptz,                    -- rotation 後の旧 DEK
  UNIQUE(user_id, retired_at)                    -- active DEK は user あたり 1 つ
);

-- sessions: cookie session
CREATE TABLE sessions (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash   bytea NOT NULL,                   -- HMAC-SHA256 (server secret, sid)
  created_at   timestamptz NOT NULL DEFAULT now(),
  expires_at   timestamptz NOT NULL,
  revoked_at   timestamptz
);
CREATE INDEX ON sessions(token_hash);
CREATE INDEX ON sessions(user_id);

-- mood_logs: 気分ログ (一部暗号化)
CREATE TABLE mood_logs (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  ts            timestamptz NOT NULL,            -- 平文 (時系列 index)
  score         smallint NOT NULL CHECK (score BETWEEN 1 AND 5),
  valence       real,                            -- -1.0 .. 1.0
  arousal       real,                            -- -1.0 .. 1.0
  tags          text[] NOT NULL DEFAULT '{}',    -- semantic id 平文
  note_cipher   bytea,                           -- 自由記述の暗号文 (nullable)
  note_nonce    bytea,
  dek_id        uuid REFERENCES user_keys(id),
  alg_version   smallint NOT NULL DEFAULT 1,
  source        text NOT NULL DEFAULT 'manual'   -- 'manual'|'evening_dialog' 等
);
CREATE INDEX ON mood_logs(user_id, ts DESC);

-- sleep_logs: 睡眠報告
CREATE TABLE sleep_logs (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  date         date NOT NULL,                    -- 起床日 (Asia/Tokyo の日付)
  bedtime_at   timestamptz,                      -- 就寝時刻 (前日 or 当日早朝)
  wake_at      timestamptz,                      -- 起床時刻
  quality      smallint CHECK (quality BETWEEN 1 AND 5),
  source       text NOT NULL DEFAULT 'manual',
  UNIQUE(user_id, date)                          -- 1 日 1 レコード
);

-- dialog_sessions: 対話セッション
CREATE TABLE dialog_sessions (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  mode          text NOT NULL CHECK (mode IN ('morning','evening','talk')),
  started_at    timestamptz NOT NULL DEFAULT now(),
  closed_at     timestamptz,                     -- system クローズ後
  close_reason  text,                            -- 'turn_cap'|'user_close'|'crisis'|'idle_timeout'
  turn_cap      smallint NOT NULL                -- mode に応じた上限 (3/5/10)
);
CREATE INDEX ON dialog_sessions(user_id, started_at DESC);

-- dialog_turns: 各ターン (暗号化必須)
CREATE TABLE dialog_turns (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  session_id      uuid NOT NULL REFERENCES dialog_sessions(id) ON DELETE CASCADE,
  user_id         uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  turn_index      smallint NOT NULL,             -- 0 始まり
  role            text NOT NULL CHECK (role IN ('user','assistant')),
  content_cipher  bytea NOT NULL,
  content_nonce   bytea NOT NULL,
  dek_id          uuid NOT NULL REFERENCES user_keys(id),
  alg_version     smallint NOT NULL DEFAULT 1,
  model           text,                          -- 'claude-haiku-4-5-20251001' 等
  ts              timestamptz NOT NULL DEFAULT now(),
  UNIQUE(session_id, turn_index)
);
CREATE INDEX ON dialog_turns(user_id, ts DESC);

-- dialog_summaries: 末尾 JSON サマリー (Mid memory)
CREATE TABLE dialog_summaries (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  session_id      uuid NOT NULL UNIQUE REFERENCES dialog_sessions(id) ON DELETE CASCADE,
  user_id         uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  date            date NOT NULL,                 -- Asia/Tokyo の対象日
  summary_cipher  bytea NOT NULL,                -- JSON (§5.3) を暗号化
  summary_nonce   bytea NOT NULL,
  dek_id          uuid NOT NULL REFERENCES user_keys(id),
  alg_version     smallint NOT NULL DEFAULT 1,
  ts              timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON dialog_summaries(user_id, date DESC);

-- crisis_events: 検知ログ (内容は保存しない、メタのみ)
CREATE TABLE crisis_events (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  session_id   uuid REFERENCES dialog_sessions(id) ON DELETE SET NULL,
  detected_by  text NOT NULL CHECK (detected_by IN ('regex','classifier','both')),
  ts           timestamptz NOT NULL DEFAULT now()
);

-- audit_log: KEK/DEK 操作のみ (デバッグ用、PII なし)
CREATE TABLE audit_log (
  id      bigserial PRIMARY KEY,
  ts      timestamptz NOT NULL DEFAULT now(),
  actor   text NOT NULL,                         -- 'system' / user_id
  action  text NOT NULL,                         -- 'dek.create'|'dek.rotate'|'kek.read' 等
  meta    jsonb
);
```

### 5.2 Blind Index は Phase 1 では不要

`mood_logs.tags` は semantic id (平文) のため通常 SQL で検索可能。自由記述 (`note_cipher`) や対話本文 (`content_cipher`) はフルテキスト検索しない方針 → Blind Index / Bloom Filter は **Phase 2 以降に延期** (§14)。

1. `null`/`undefined`/`''` → `''`

  // 自傷

挙動 (§7.5 に再掲):
- いずれか 1 つでも hit したら `hit: true`、`matched` に id を返す
- 大文字小文字無視・全角半角混在対応のため、検出前に `text.normalize('NFKC').toLowerCase()` を通す
- `OD` のような短い語は単語境界配慮 (`\bOD\b`) で false positive を抑える
- 該当語が **assistant 発話に含まれる** ケースも検出対象とする (LLM が誤って復唱した場合の保険)

**classifier**: Phase 1 では Haiku 4.5 へ短い prompt で yes/no 判定を別呼。コストは月数円なので OK。`detectCrisis` は regex hit を最優先 (LLM 結果待たず即返却)、regex hit なし時のみ classifier 呼ぶ。

### 6.10 認証 (Magic link)

- メール送信は Resend (`RESEND_API_KEY` env)。失敗時はサーバログだけ残し 200 を返す (enumeration 防止)。
- token は 32 bytes random、`magic_tokens` テーブル (本書未掲載、migration 内で定義) に HMAC で保存、30 分 TTL、1 回使用。
- 検証成功で `sessions` レコード作成、cookie 設定、`/` に 302。
- Phase 1 では Touri 1 人なので `allowed_emails` env で許可リスト制御 (`TOMORI_ALLOWLIST=touri1705@outlook.com`)。許可外 email の magic request は 200 だが内部で実際送らない。

  consumed_at  timestamptz

## 7. 挙動仕様 (Reviewer はここからテスト生成)

### 7.1 気分ログ Quick log

- 7.1.1 `POST /api/mood` で `score=4, tags=['work','focus_high']`、note 省略 → 201 でレコード作成、`note_cipher = null` で保存される。
- 7.1.2 `note` を 5 文字付与 → `note_cipher` と `note_nonce` が non-null で保存。
- 7.1.3 `tags` に MOOD_TAGS にない `'xyz'` が含まれる → 400 `VALIDATION_FAILED`、保存されない。
- 7.1.4 `tags` を 9 件指定 → 400 `VALIDATION_FAILED`。
- 7.1.5 `score=0` または `score=6` → 400 `VALIDATION_FAILED`。
- 7.1.6 `score=3, valence=1.5` → 400 `VALIDATION_FAILED` (range)。
- 7.1.7 未認証 (cookie なし) で POST → 401 `UNAUTHORIZED`、DB 変更なし。
- 7.1.8 `X-Tomori-Csrf` ヘッダなしで POST → 403 `FORBIDDEN`。
- 7.1.9 別ユーザーの user_id でリソースを偽装することはできない (`user_id` は cookie session から決定、リクエスト body の `user_id` は無視)。
- 7.1.10 `GET /api/mood?from=2026-05-01&to=2026-05-11` → ts 範囲内のレコードのみ、`note` は復号済プレーンテキストで返る。
- 7.1.11 `from > to` → 400 `VALIDATION_FAILED`。
- 7.1.12 `note` に 2001 文字 → 400。2000 文字ちょうどは 201。

### 7.2 睡眠報告

- 7.2.1 `POST /api/sleep` で `date='2026-05-11', wake_at='2026-05-11T07:30:00+09:00', quality=4` → UPSERT、(user_id, date) で一意。
- 7.2.2 同日に 2 度目の POST で `quality=3` のみ → 既存レコードの quality だけ更新、bedtime_at/wake_at は維持。
- 7.2.3 `date` に `2026/05/11` → 400 `VALIDATION_FAILED`。
- 7.2.4 全フィールド省略 → 400 (refine `at least one of ...`)。
- 7.2.5 `quality=6` → 400。
- 7.2.6 `GET /api/sleep?date=2026-05-11` → 該当 1 件、無ければ `{ ok: true, data: null }`。

### 7.3 朝対話 (`/api/dialog` mode='morning')

- 7.3.1 `POST /api/dialog/start { mode: 'morning' }` → `dialog_sessions` 作成、`turn_cap=3`、`dialog_turns` に index=0, role='assistant' の挨拶ターンが入る。レスポンスに `assistant.text` が返る。
- 7.3.2 続けて `POST /api/dialog/:id/turn { text: 'まあまあ' }` → user turn(index=1) と assistant turn(index=2) が増える。`remaining_turns = 1` (assistant 2 ターン消費後、残り 1)。
  - 注: ターン消費の数え方は **assistant の発話数**。turn_cap = 3 は assistant 発話 3 回まで。
- 7.3.3 3 回目の `turn` → assistant のクロージング発話が返る (`kind: 'closing'`、summary は `{...minimal}` で `closed_by: 'turn_cap'`)。`dialog_sessions.closed_at` がセット、`close_reason='turn_cap'`。
- 7.3.4 4 回目の `turn` → 409 `TURN_CAP_REACHED`、DB 変更なし。
- 7.3.5 morning では `save_summary` tool は **与えない**。summary は最小サマリー (`{ insights: '', action_item_tomorrow: <assistant の最後の発話を要約してサーバが詰める or 空文字>, ... }`) を保存。
- 7.3.6 LLM が `[CRISIS_DETECTED_BY_MODEL]` を返した → §7.5 crisis フローへ。
- 7.3.7 LLM タイムアウト (25s 超) → 504 `LLM_TIMEOUT`、user turn は DB 保存済だが assistant 発話は保存されない (rollback)。

### 7.4 夜対話 (mode='evening')

- 7.4.1 `POST /api/dialog/start { mode: 'evening' }` → `turn_cap=5`、最初の assistant 発話が返る。
- 7.4.2 4 ターン目までは通常進行 (`kind: 'continue'`)。
- 7.4.3 5 ターン目の `POST /api/dialog/:id/turn` で LLM が `save_summary` tool を呼んだ → サーバが
  1. tool input を zod validate
  2. validate OK → `dialog_summaries` に暗号化保存
  3. assistant の closing 発話を生成 (tool 呼出と同 messages.create のテキスト部分があればそれ、無ければ追加 1 回呼んでクロージング文を作る)
  4. `dialog_sessions.closed_at`, `close_reason='turn_cap'` 設定
  5. レスポンス `kind: 'closing'`, `summary` 入り
- 7.4.4 LLM が `save_summary` を呼ばなかった (例: 4 ターン目で勝手に呼んだ、または最後まで呼ばなかった) → サーバ側で 5 ターン目終了後にもう 1 回 LLM を呼んで `tool_choice: { type: 'tool', name: 'save_summary' }` 強制 → それでも失敗したら最小サマリー fallback (`insights: '生成失敗'`)。
- 7.4.5 tool input が schema 違反 → 1 回再試行、ダメなら最小サマリー fallback。
- 7.4.6 `unresolved_concerns` が 81 文字 → 1 回再試行、ダメなら 80 文字に truncate して保存。
- 7.4.7 `POST /api/dialog/:id/close { reason: 'user_close' }` を 3 ターン目で受領 → サーバが追加 1 回 LLM 呼出して `save_summary` 強制 → 保存 → `close_reason='user_close'`。
- 7.4.8 同セッションに 2 度目の close → 409 `SESSION_CLOSED`。

### 7.5 危険発言検知 (全 mode 共通)

- 7.5.1 ユーザー発話に `'死にたい'` を含む → `detectCrisisRegex` が hit → assistant 発話を LLM に作らせない → `crisis_events` 記録 → `dialog_sessions.closed_at`, `close_reason='crisis'` 設定 → レスポンス `kind: 'crisis', crisis_card: {...}`、HTTP 409 `CRISIS_HANDOFF`。
- 7.5.2 `'リスカ'` → §7.5.1 と同じ挙動。
- 7.5.3 `'リスト　カット'` (全角空白挟む) → 7.5.1 と同じ挙動 (NFKC + lower 正規化後 `'リストカット'` を含む regex には hit しない、想定通り)。**ただし** `'リス　トカット'` のような分割は対応外であることを明示テスト (false negative の存在を仕様化)。
- 7.5.4 `'今日は死ぬほど忙しい'` → `'死ぬ'` は regex セットに無いので false 扱い (regex 段では non-hit)。classifier が yes なら crisis、no なら通常進行。
- 7.5.5 assistant が `[CRISIS_DETECTED_BY_MODEL]` を返したとき → サーバが「LLM 由来 crisis」とみなし 7.5.1 と同じフロー (`detected_by='classifier'` で記録)。
- 7.5.6 crisis card のコンテンツは static、LLM に生成させない。フィールドは §6.4 `CrisisCard` の通り。固定 hotlines は §11.1 環境設定で持つ。
- 7.5.7 crisis 検知後の同セッションへの `turn` POST → 409 `SESSION_CLOSED`。
- 7.5.8 crisis 後 30 分以内に同ユーザーが新規 `dialog/start` → 通常通り作成可。ただし新セッションの最初の assistant 発話 system prompt に「直近で危険な兆候があったことを認識し、落ち着いた声掛けから始めて」と prepend する。

### 7.6 AI 相談 (mode='talk')

- 7.6.1 `turn_cap=10`。1〜6 ターン目は通常進行。
- 7.6.2 7 ターン目で assistant 発話は「ここまでの気づき」を 1 文挟む (system prompt 指示)。
- 7.6.3 10 ターン目 assistant 発話で「今日はここまで」を明示、`closed_at` 設定、`close_reason='turn_cap'`。summary は生成しない (talk モードは summary なし)。
- 7.6.4 ロールプレイ要請 (`'恋人になって'`) → assistant は穏やかに拒否 (system prompt)。**実装は LLM 任せのため**、Reviewer のテストは「拒否ワードを含むユーザー入力に対して、assistant 発話の token 制限内で完了する (=エラーにならない)」までの確認に留める。テキスト内容の精密な検証は flaky なので避ける。

### 7.7 階層メモリ

- 7.7.1 `buildContext` に渡す Short は **直近 7 日以内の dialog_turns**、最大 30 turn (token 節約)。30 を超える場合は古いものから drop。
- 7.7.2 Mid は **直近 14 日の dialog_summaries**、最大 14 件。古い順から drop。
- 7.7.3 `buildContext` の出力は単一 `user` role の text。形式:
  ```
  ## 直近のサマリー (Mid memory, 最大 14 件、新しい順)
  - 2026-05-10 sentiment=0.7 emotions=[calm,accomplished] events=[blog書けた,...]
  - ...
  
  ## 直近の対話片 (Short memory, 最大 30 ターン、新しい順)
  - (2026-05-10 22:30) [user] 今日は疲れた
  - (2026-05-10 22:30) [assistant] そうだったんだね...
  - ...
  
  ## 今日の睡眠/気分
  - sleep: bed=23:30 wake=07:15 quality=3
  - mood: 08:12 score=3 tags=[work]
  ```
- 7.7.4 Mid/Short ともに 0 件でも問題なく動く (空セクションを出力)。
- 7.7.5 LLM 入力前に **maskPII を context 全体に通す**。
- 7.7.6 user 発話自体も LLM 送信前に maskPII を通す。assistant 発話はマスクしない (LLM 生成物には PII は混ざらない想定)。

### 7.8 maskPII (LLM 境界)

- 7.8.1 `maskPII(undefined)` → `''`
- 7.8.2 `maskPII(null)` → `''`
- 7.8.3 `maskPII('')` → `''`
- 7.8.4 `maskPII('連絡先は abc@example.com です')` → `'連絡先は [EMAIL] です'`
- 7.8.5 `maskPII('090-1234-5678 まで')` → `'[TEL] まで'`
- 7.8.6 `maskPII('03-1234-5678 と 080-0000-0000')` → `'[TEL] と [TEL]'`
- 7.8.7 `maskPII('カード 4242424242424242 を使った')` → `'カード [CC] を使った'`
- 7.8.8 `maskPII('４２４２４２４２４２４２４２４２')` (全角) → そのまま (全角は対象外、§7.8.16)
- 7.8.9 `maskPII('a@b.co と c@d.co')` → `'[EMAIL] と [EMAIL]'`
- 7.8.10 `maskPII('連絡先 [EMAIL] です')` → `'連絡先 [EMAIL] です'` (既存マスクはそのまま)
- 7.8.11 `maskPII('https://example.com/path?a=1')` → 同じ (URL は残す)
- 7.8.12 `maskPII('not-an-email-@-x')` → 同じ (regex 不一致)
- 7.8.13 `maskPII('0312345678')` → `'[TEL]'` (ハイフンなしも対象)
- 7.8.14 `maskPII('1234567890123')` Luhn 不通 → 同じ
- 7.8.15 `maskPII('4242 4242 4242 4242')` (半角空白区切り) → 内部正規化を経て CC 検出。`'[CC]'`。
- 7.8.16 全角の `'０９０－１２３４－５６７８'` → そのまま。**仕様として false negative を許容**。

### 7.9 暗号化境界

- 7.9.1 ユーザー作成時に DEK が 1 つ作られ `user_keys` に保存される (`retired_at` is NULL = active)。
- 7.9.2 `encrypt(dek, plaintext, aad)` の戻り値を `decrypt(dek, blob, aad)` で復号 → 元と一致。
- 7.9.3 `aad` を別 user_id に変えて decrypt → AES-GCM auth tag 違反で throw。
- 7.9.4 `nonce` の 1 バイトを変えて decrypt → throw。
- 7.9.5 `ciphertext` の 1 バイトを変えて decrypt → throw。
- 7.9.6 KEK プロバイダを `env → kms` に切り替え (テストでは `byId` モック) → 既存 DEK を **`kek_id` から判定して** 復号可能。
- 7.9.7 `POST /api/account/delete { confirm: 'DELETE' }` で:
  - 7.9.7a user_keys を全削除 (ON DELETE CASCADE で他テーブルも自動削除)
  - 7.9.7b users.deleted_at をセット (email は anonymize: `deleted-<uuid>@tomori.local` に書き換え)
  - 7.9.7c 同 user の cookie session を全 revoke
  - 7.9.7d 以後の `/api/me` は 401
- 7.9.8 confirm が `'delete'` (小文字) → 400 `VALIDATION_FAILED`、削除されない。
- 7.9.9 `GET /api/export` → mood/sleep/dialog_turns/dialog_summaries をすべて復号して JSON で返す。content-type: `application/json; charset=utf-8`。

### 7.10 認証境界

- 7.10.1 `POST /api/auth/magic/request { email: 'touri1705@outlook.com' }` → 200。実際にメール送信。
- 7.10.2 `POST /api/auth/magic/request { email: 'other@example.com' }` (allowlist 外) → 200。**メールは送らない**。レスポンスは同一。
- 7.10.3 magic token は 30 分 TTL。31 分後の verify → 400 `VALIDATION_FAILED`。
- 7.10.4 同 token を 2 度 verify → 1 度目 302、2 度目 400 (consumed)。
- 7.10.5 `POST /api/auth/logout` → 200、session revoke、cookie に `Max-Age=0` を返す。
- 7.10.6 session cookie が改ざんされた (HMAC 不一致) → 401。
- 7.10.7 session の `expires_at` 超過 → 401。

### 7.11 Rate limit

- 7.11.1 1 ユーザーが `/api/dialog/:id/turn` を 1 秒に 2 回 POST → 2 回目は 429 `RATE_LIMITED`。実装は Hono の in-memory token bucket (1 RPS、burst 1)。Phase 1 は 1 ユーザーなので Redis 不要。
- 7.11.2 1 ユーザーが `/api/mood` を 1 秒に 3 回 POST → 3 回目 429。bucket 設定: 5 RPS, burst 5。
- 7.11.3 `/api/healthz` には rate limit 適用しない。

### 7.12 セキュリティヘッダ / CSP

`secureHeaders` middleware 設定:

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';      ← Tailwind/Konsta の inline style 許可
  img-src 'self' data:;
  connect-src 'self';
  frame-ancestors 'none';
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

- 7.12.1 任意の origin から `/api/me` を fetch with credentials → CORS で reject (allow-origin: `https://tomori.<host>` のみ)。
- 7.12.2 POST に `Origin` ヘッダなし → 403 `FORBIDDEN`。

### 7.13 履歴とエクスポート

- 7.13.1 `GET /api/history?date=2026-05-11` → `{ mood: MoodLogView[], sleep: SleepLogView|null, summaries: DialogSummary[] }`。
- 7.13.2 date 未来日 → 200 で空集合。
- 7.13.3 date 形式不正 → 400。

- 7.14.1 `/` 初回表示 (login 済) → キャラ orb が表示され (`<img alt="tomori orb">` exists)、4 つの CTA カード (`<button>朝の対話</button>` 等) が並ぶ。
- 7.14.2 「気分を記録」をクリック → `/mood` に遷移、Likert 5 つのボタンが表示。
- 7.14.3 Likert `4` → タグ `work` → 「保存」 → トーストが出て `/` に戻る (`<div role="status">保存しました</div>` が一時表示)。

## 14. 不採用案 (検討して却下した設計)

| 案 | 却下理由 |
|---|---|
| **A. Next.js Server Actions / API Routes でバックエンドを兼ねる** | Phase 1.5 で Capacitor ラップ予定。`output: 'export'` で Server Actions 不可。最初から Hono に分離するのが将来コスト最小 |
| **B. Prisma を使う** | Phase 1 はテーブル数 9、生 SQL + pg で十分。Prisma の `bytea` 取り扱い癖 (knowledge/gotcha/prisma-geography-deserialize-error.md 系) を避ける。Phase 2 で必要になったら移行 |
| **C. pgcrypto / Postgres TDE で済ます** | knowledge/pattern/envelope-encryption-postgres-node.md 通り、pgcrypto はクエリログに鍵が残る。アプリ層 envelope encryption が筋 |
| **D. PHQ-9 マイクロサーベイを Phase 1 で組み込む** | 過剰検知のリスク + 1 人ユーザー検証では不要。Phase 2 で一般公開検討時に再評価 |
| **E. RAG / Long memory を Phase 1 で実装** | Short(7d) + Mid(14d) で 1 人ユーザー検証には足りる。RAG は embedding コスト + 検索品質チューニングが Phase 1 のゴールから外れる |
| **F. Weekly digest cron を Phase 1 で実装** | 効果検証は Mid summary を `/history` で見れば十分。cron は Phase 1.5 で push と一緒に入れる |
| **G. APNs / Local 通知 / Apple Developer 加入を Phase 1 で** | 「Web 完結」で検証可能、Apple Developer $99/年は検証成功後に払う方が合理的 |
| **H. HealthKit / Watch 連携 / Capacitor を Phase 1 で** | Phase 1 の体験は能動起動の Web で完結する。Capacitor は Phase 1.5 で `output: 'export'` 完成品をラップする方が安全 |
| **I. Google Calendar / Gmail 統合** | OAuth 同意・スコープ審査・LLM の context 設計が重い。Phase 2 で別設計 doc |
| **J. ZDR 契約 (Anthropic Enterprise)** | 標準 30 日削除 + 学習不使用で個人検証には十分。コスト + 個人での申込不可 |
| **K. Critical Alerts entitlement 申請** | 却下確率高 + 必要性低。Phase 1.5 でも申請しない方針 |
| **L. Replika 型キャラ (恋愛・擬人化)** | 依存形成リスクの実証事故あり (knowledge/pattern/cbt-ai-companion-dialog.md)。orb 抽象シンボル + AI 境界明示で代替 |
| **M. VUI (音声のみモード)** | Phase 1 は Web 完結 + 開発コスト高。Phase 2 以降で再検討 |
| **N. aisaba 系ダーク基調デザイン言語を tomori にも適用** | tomori は「柔らかいライト基調 (Day One/Stoic 系)」が要件。aisaba 系とは別アイデンティティ。両者を意図的に分ける |
| **O. キャラを Lottie / Rive で動的レンダ** | バンドルサイズ + WebView 安定性 + Phase 1 では CSS animation で十分表現できる |
| **P. Blind Index / 検索可能暗号 (CipherSweet 等)** | Phase 1 では mood note / dialog turn の検索ユースケースなし。Phase 2 で必要になったら導入 |
| **Q. マルチユーザー / 招待リンク / 公開 UI** | Touri 1 人検証が目的。allowlist 1 件で十分 |
| **R. Magic link 以外の認証 (Google OAuth / Passkey)** | 1 人ユーザーで Resend + Magic で摩擦最小。Phase 2 公開時に再検討 |
| **S. Server-Sent Events / WebSocket でストリーミング応答** | UX 良いが Phase 1 では request-response 1 ターンで十分高速 (Haiku は速い)。Coolify Nginx の SSE 設定追加コストを回避 |
| **T. Streak / gamification** | 義務感を生むため Touri 個人検証には逆効果。Mid summary の事実だけで内発動機を作る (knowledge/pattern/mood-log-schema-llm-ready.md) |

## 16. 開発・レビュー時のチェックポイント (Developer / Reviewer 用)

### 16.1 Developer (Codex) への強調

1. **`output: 'export'` 縛りを 1 行も破らない** (next/image, middleware, Server Actions, ISR, next/headers すべて禁止)
2. **エンドポイント単位で zod スキーマを必ず通す** (§6.3)
3. **`runLLM` を呼ぶ前に必ず `maskPII` を context 全体に適用する** (§7.7.5, §7.7.6)
4. **crisis 検知は LLM 呼出より先に regex で判定**、hit したら LLM を呼ばない (§7.5.1)
5. **`save_summary` tool は evening のみ** (§6.6, §7.4)
6. **Hono の onError で `err.status` を使う** (gotcha 既知)
7. **暗号化の AAD に必ず user_id を入れる** (§6.8)
8. **`/api/account/delete` は user_keys 削除を最優先** (右-to-erasure)

### 16.2 Reviewer (Codex) への強調

1. **§7 をテストケース生成の起点に使う**。番号は安定 ID として参照可
2. **maskPII の全ケース (§7.8.1–7.8.16) は unit で 16 件すべてカバー**
3. **crisis regex は patterns.ts の全 id について hit / non-hit のペアテスト**
4. **dialog turn テストは LLM をモックする** (実 API は CI で叩かない)
5. **E2E は §7.14 の 10 シナリオを `e2e/scenarios/` Markdown で再現**
6. **暗号化テストは AAD 改ざん・nonce 改ざん・ciphertext 改ざんの 3 ケース必須** (§7.9.3–7.9.5)
7. **削除フローは「DEK が物理削除されている」をテストで直接 SELECT 確認**
8. **error code は §6.2 のテーブル通り。`AppError.status` と `code` の対応をテストで網羅** (gotcha/hono-error-middleware-apperror-status.md 既知)
